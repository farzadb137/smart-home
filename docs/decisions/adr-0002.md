# ADR 0002 — ESP32-C6 + MQTT as the device protocol

- **Status:** Accepted
- **Date:** [TODO: YYYY-MM-DD]
- **Deciders:** Farzad

## Context

Devices need reliable bidirectional communication with the hub over WiFi: telemetry up, commands down, child-node traffic behind a parent device, and status/online detection. Candidate patterns: raw HTTP polling, WebSockets, CoAP, MQTT.

## Decision

All device ↔ hub communication uses **MQTT** against a Mosquitto broker on the hub, with the topic scheme defined in `protocol/mqtt-topics.yaml` (prefix `home`, per-device subtrees, retained status, `home/time` sync). ESP32-C6 is the device SoC.

## Consequences

**Positive**
- Pub/sub decouples devices from hub implementation; devices never address each other or the backend directly.
- Retained messages give instant state on (re)connect; Last Will gives offline detection.
- ACLs per device give per-unit authorization in one place (broker config).
- Child nodes map naturally onto topic sub-trees (`children/{child_id}/...`).
- MQTT clients are mature and memory-friendly on ESP-IDF.

**Negative / risks**
- Adds a broker as a critical hub component (must be supervised and backed up).
- Topic/ACL management needs tooling as device count grows.
- MQTT is not end-to-end encrypted by default — TLS is a planned step (progressive security).

**Alternatives considered**
- *HTTP polling* — simple but wasteful for telemetry, no server-push for commands.
- *WebSockets* — push yes, but no built-in retained state/offline detection, per-connection state on the hub.
- *CoAP* — lightweight, but weaker ecosystem/tooling for our use case.
